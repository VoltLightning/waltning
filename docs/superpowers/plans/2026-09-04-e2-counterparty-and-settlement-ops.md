# E2 · Counterparty and settlement operations, the phone half — Implementation Plan (wave 4a)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Read `2026-09-04-wave-4-shared.md` first.

**Goal:** Six operations get a Zod input in `core` and a local executor in `ledger`: `create_counterparty` `update_counterparty` `merge_counterparties` `unmerge_counterparties` `record_distinct_counterparties` · **`settle_debt`**. A settlement takes the amount that changed hands and the debt it discharges — never the residual — and returns the residual.

**Architecture:** Identical to A3 — one executor per file, inputs in their own delimited block, registered in a delimited block. Two new replica tables, shared-schema first (`packages/schema/src/*.pg.ts` + `*.sqlite.ts`, parity type-test, `pnpm db:generate` → migration `0007`, `pnpm ledger:generate` → `ddl.ts`): **`counterparty_merges`** (`id`, `winner_id`, `loser_id`, `moved_transaction_ids` as JSON text, `merged_at`, `unmerged_at` nullable) — the record S15 §9.2 says makes unmerge exact; **`counterparty_distinct_pairs`** (`a_id`, `b_id`, ordered so `a < b`, PK on the pair) — S15's *these are different* decision. The unique index on the normalised name (`counterparties_name_uq`, Postgres) gets its SQLite twin: a generated `name_folded` column is not available in the replica's Drizzle dialect, so the executor refuses on `fold(name)` collision **and** a unique index on `lower(trim(name))` is added as an expression index in `counterparties.sqlite.ts` (Drizzle supports `sql` in `uniqueIndex().on()`); break it once.

**Spec:** `operations.md` (counterparties row, `settle_debt` row, H9) · `SPEC.md` §6.6 (settlement table, sign rule), §6.7 · `screens/S15` §5, §6, §9 · `S14` §3, §5, §6 · `architecture/08` H9, H13 · `computations.md` §7.

**Board cards closed:** *Writes — counterparties (5 ops)* · *Writes — debt and settlement (2 ops)* (`settle_debt` here; the second, reassignment, is `debt_reassignments` — a server-only migration table by `0004`'s own comment, fed by the import on `#e8`; the card's write-up says so).

**Branch:** `feature/e2-counterparty-ops` off `main`.

## Tasks

1. **Inputs.** `/* ── counterparties and settlement ── */`: `createCounterpartyInput { id, name (trim 1..120), kind: person|company (default person), settlementCurrency: currency | null, contact: string|null (max 200), note (max 2000, default "") }`; `updateCounterpartyInput { id, version, patch: strict partial of the above minus id, ≥1 key }`; `mergeCounterpartiesInput { mergeId: zId<"counterpartyMerges">, winnerId, loserId }` refine distinct; `unmergeCounterpartiesInput { mergeId }`; `recordDistinctCounterpartiesInput { aId, bId }` refine distinct; **`settleDebtInput { id: zId<"transactions">, counterpartyId, accountId, date, amount: zMoney (positive), currency, discharges: { currency, amount: zMoney positive }, note (default ""), categoryId?: zId<"categories"> }`** — no residual field exists, by design. Add `counterpartyMerges` to `IdTable`. Refusal test per schema.
2. **Counterparty executors.** `create` refuses a folded-name collision with a live counterparty (message names the existing one — `MatchWarning` is the screen's; the executor's refusal is the exact-collision case S15 §6 assigns to the index); `update` version-checked, refuses archiving while any §7 balance is non-zero (S15 §6 *Gated*; use E1's fold if merged, else the same two-line sum inline with a comment naming `counterpartyBalance`); `merge` moves every live transaction's `counterparty_id` from loser to winner, records the moved ids in `counterparty_merges`, archives the loser, refuses if either is archived or the pair is recorded distinct; `unmerge` reverses exactly the recorded ids (skipping any since soft-deleted, counting them in the result), un-archives, stamps `unmerged_at`, refuses a merge already unmerged; `record_distinct` inserts the ordered pair, idempotent.
3. **`settle_debt`.** `mints: [input.id]`. Read the live balance in `discharges.currency` for the counterparty (E1's reader or the inline fold). Refuse when zero (*nothing to settle in {currency}*). **Direction from the balance's sign:** positive (they owe you) → the row is `income` into `accountId`; negative → `expense` from it. Write one transaction through the exported `insertTransaction`: `type`, `amountOriginal = amount`, `currency`, `counterpartyId`, `counterpartyRole: "debt"`, `debtCurrency = discharges.currency`, `debtAmount = discharges.amount`, `payee = counterparty.name`, `categoryId` when given, `source: "manual"`. Compute `residual = balanceAfter` (re-fold) and return `{ row, residual, overSettled: sign flipped }`. The implied rate is `discharges.amount ÷ amount`, derived by the screen (§7.5) and never stored. Tests: the S14 worked example (owe 120 EUR, settle 50 EUR → residual −70); exact clear → 0; over-settlement flips sign and is **not** refused; zero balance refused; a `contribution` row never counts.
4. **Session, port, controller.** Six session methods, six port methods, controller methods returning `{ id } | { fieldErrors }` (`settleDebt` returns `{ id, residual, overSettled }`). Snapshot `counterparties` grows to carry `kind`, `settlementCurrency`, `archived` (S12/S13/S15 all read them). `listCounterparties({ includeArchived })`.
5. **Allowlist and DDL.** `packages/schema` gains the two table pairs (flat, `.pg.ts`/`.sqlite.ts`); parity type-test; `ddl.ts` regenerated; `migrate.test.ts` green. `packages/ledger/src/counterparties/` already exists.
6. **Report.** Commit, push `feature/e2-counterparty-ops`; report PR *"People, and settling up with them — the phone half"*, quoting both cards, the S14 spec correction, and the reassignment note.
